# DS004 Web Publishing Agent

## Introduction

The `web-publishing` agent is the Basic catalog agent that owns Explorer QA and production public topology. Its canonical Ploinky agent id is `agent:basic/web-publishing`. It replaces the Explorer QA/prod dependency on `basic/cloudflared` with a provider-backed publishing control plane that can generate public URLs before sibling agents resolve their environment.

## Core Content

The manifest must use the immutable custom image `docker.io/assistos/web-publishing-agent:node24-nginx-cloudflared@sha256:f0f83dc406bc0434ccbeac48dc826cdb8c527a637a5bf1b5ddf915110d24c477`. That image supplies the Ploinky Node runtime, nginx, and the Cloudflare `cloudflared` binary. The long-lived process is `node /code/runtime/supervisor.mjs`; the Ploinky AgentServer sidecar starts through `node /code/runtime/wait-for-nginx.mjs && sh /Agent/server/AgentServer.sh`. The gate does not start AgentServer until Nginx accepts TCP on container loopback port `8081`, after which Ploinky performs MCP readiness against AgentServer.

Nginx is a required child, not a best-effort sibling of the supervisor. A missing executable, spawn error, or exit at any code must write the overall status as `failed`, terminate the remaining child within a bounded deadline, and make the supervisor process exit nonzero. Token mode and a provisioned `cloudflare-api` mode require a scoped tunnel token and a live `cloudflared` child; a missing token or connector exit is equally fatal. An API mode with no tunnel or token keeps Nginx and the admin control plane available but records both overall and connector state as `awaiting-provision`, never `running`. Plain `nginx` mode must not spawn `cloudflared` and records it as `disabled`, even if an unused token is present. The supervisor must materialize the connector token only in an ephemeral mode-`0600` file inside a private mode-`0700` directory and invoke a compatible pinned Cloudflared with `--token-file`; it must not place the real token in child argv, a long-lived child environment, status, or logs. Immediately after capturing the startup token it must scrub Cloudflare credential variables from its own mutable environment. The Nginx version probe and long-lived child must receive an environment with Cloudflare secret fields removed. `SIGINT` and `SIGTERM` write a stopping status, signal every live child, escalate after a bounded grace period, and exit the supervisor; successful child termination records `stopped`, while a child that survives `SIGKILL` records `failed` and returns nonzero. The supervisor must not use an idle timer to remain healthy after its data-plane children disappear.

The agent must not declare `routerAccess`, `httpServices`, `guest`, `ssoProvider`, or top-level `ports`. The control plane is Explorer admin settings plus admin MCP tools. Every profile maps AgentServer container port `7000` first through stable loopback-only box-side port `17003` (`127.0.0.1:17003:7000`), so the generic Ploinky route resolves MCP to AgentServer rather than to a data-plane listener. The default data-plane profile retains the ordinary Nginx listener and the external-proxy connector on host loopback through `profiles.default.openPorts`. A separate `lan` profile may bind only the ordinary Nginx port to `0.0.0.0` as an explicit reviewed data-plane exposure; the AgentServer and external-proxy connector remain host-loopback-only. This does not create a public dashboard route or non-loopback MCP/control route.

The manifest uses the canonical bridge contract with `webmeet-signaling` as its primary attachment and `office-publishing` as its secondary attachment. It declares no aliases: Ploinky derives `web-publishing` from the canonical agent id and registers it on both networks. Nginx reaches LiveKit as `livekitserveragent:7880` only on `webmeet-signaling`, reaches the OnlyOffice editor proxy as `onlyoffice:8080` only on `office-publishing`, and reaches the router through the generic `ploinky-router:8080` gateway. These names are DNS identities only; every upstream retains an explicit port. The fixed origin allowlist rejects `host.containers.internal` and other host-gateway or undeclared sibling paths.

Persistent state is mounted from `.ploinky/data/web-publishing` at `/data`. The image runs as a non-root user (UID/GID 999 in the pinned image), so the manifest uses the generic volume option `chmod: 1023` (`01777`, world-writable with the sticky bit) and `podmanChown: false`. This lets a fresh Linux Docker bind mount and a rootless Podman bind mount accept atomic writes from the container user without transferring ownership of the host directory. The sticky bit prevents unrelated local users from deleting or replacing files they do not own. Container-written config and status files remain non-secret and world-readable under the image's `0022` umask so the host-side provider can read `config.json`; `secret-state.json` remains mode `0600` and is read only by the container supervisor and admin tools. The host-side provider must never open or depend on that container-owned secret-state file.

The manifest must expose one admin-only Explorer settings entry with key `web-publishing-settings`, label `Web Publishing`, plugin key `web-publishing/web-publishing-settings`, and settings component `web-publishing-settings`. The corresponding plugin lives under `web-publishing/IDE-plugins/web-publishing-settings/` and uses admin MCP tools for reads, validation, and apply operations. The dashboard must show secret state as present or missing and must not render saved tokens back to the browser. Every MCP tool that accepts `config` must enumerate the supported nested config, tunnel, and exposure properties in `mcp-config.json`; an unshaped `{type: "object"}` is forbidden because AgentServer's strict Zod conversion strips its unknown nested fields before the tool command receives them.

The provider contract is declared through `providesConfig`. Local/default configuration has a canonical OnlyOffice route at `http://office.localhost:8081` and one real signaling route at `ws://127.0.0.1:8081/rtc`. It emits both `ONLYOFFICE_PUBLIC_URL=http://office.localhost:8081` and `WEBMEET_TURN_HOST=127.0.0.1` explicitly so previous direct-port or public provider values cannot survive a transition back to local mode. Nginx preserves the incoming host and non-default port in `X-Forwarded-Host` on ordinary HTTP origins so Document Server-generated browser URLs remain reachable. Legacy saved topology containing only the LiveKit route is upgraded with the canonical local or base-domain Office route during normalization. OnlyOffice always owns the root of its dedicated canonical hostname (`office.localhost` locally or `office.<baseDomain>` publicly); custom hosts and path-mounted routes are rejected because the provider URL and Document Server asset/WebSocket URLs must address the same proxy boundary. Local mode emits no public TLS, media-IP, TURN external-IP, or peer-allowlist values. Public configuration is fail-closed: it requires `WEB_PUBLISHING_BASE_DOMAIN`, an explicit `WEB_PUBLISHING_TLS_EDGE` contract (`cloudflare` for a Cloudflare mode or `external` for plain nginx), `WEB_PUBLISHING_LIVEKIT_MEDIA_IP`, and `WEB_PUBLISHING_TURN_EXTERNAL_IP`. Both IP inputs must be bare unicast, non-loopback IPv4 addresses; unspecified, loopback, link-local, multicast, and reserved-class values are rejected. An external TLS edge also requires deployment-owned `WEB_PUBLISHING_EXTERNAL_PROXY_CIDRS`; it is a comma-separated list of at most 16 exact IPv4 `/32` or IPv6 `/128` proxy peers and is deliberately not mutable through dashboard/MCP drafts. The provider must never infer a trusted edge, proxy peer, or public IP and must never replace invalid public input with local values.

Deployment env is authoritative over persisted dashboard topology, and one shared merge function must feed the provider, supervisor, and saved-state MCP reads so advertised and served routes cannot diverge. A missing config file represents no saved override and must not inject local defaults ahead of env. Persisted normalized exposure services are derived from `originId`, never operator-owned overrides, so saved-state reads discard those copies and recompute the current canonical origin service before validation. If the env-owned base domain changes, concrete persisted exposures from the old domain are discarded and the canonical exposure set is regenerated for the new domain. Explicit `config_validate` and `config_apply` request payloads remain input-authoritative for validation, while subsequent saved-state reads still apply the active deployment env contract.

The AgentServer sidecar must not claim that persisting configuration hot-reloaded the independently supervised data-plane children. At startup the supervisor writes a SHA-256 fingerprint of the normalized, non-secret runtime topology it actually launched. The fingerprint includes only the connector's non-secret `source`, `tokenSet` presence flag, `tunnelId`, and `tunnelName`; it must never include a token or credential. `config_apply` compares the requested fingerprint with that active value. A mismatch—including a requested connector/tunnel identity change—persists the draft, returns `applied: false` and `restartRequired: true`, and the dashboard must stop before invoking tunnel apply. The dashboard preserves these hidden non-secret tunnel fields after refresh so an API bootstrap followed by restart can perform an ordinary matching apply without losing connector identity. Tunnel apply repeats the comparison under the same cross-process operation lock and must return before its first Cloudflare HTTP request, including tunnel creation, when the fingerprint or required Nginx state does not match. An unprovisioned `cloudflare-api` topology keeps the admin control plane available but reports overall and connector state `awaiting-provision`, never `running`. Once that matching state is active, tunnel apply may create the tunnel and persist its private token, but it must not put ingress or DNS records and must require a restart for the connector. Only an apply that observes the matching fingerprint, overall `running` state, and both Nginx and Cloudflared running may mutate Cloudflare ingress and optional DNS and return `applied: true`. Config, status, and secret writes use atomic replacement and per-file locks; config and tunnel apply share the operation lock so desired-state changes cannot race the compare-and-remote-apply sequence.

The canonical public outputs are `WEBMEET_PUBLIC_LIVEKIT_URL=wss://meet.<baseDomain>`, `WEBMEET_LIVEKIT_NODE_IP=<WEB_PUBLISHING_LIVEKIT_MEDIA_IP>`, `WEBMEET_TURN_HOST=turn.<baseDomain>`, `WEBMEET_TURN_EXTERNAL_IP=<WEB_PUBLISHING_TURN_EXTERNAL_IP>`, and `WEBMEET_TURN_ALLOWED_PEER_IPS=<WEB_PUBLISHING_LIVEKIT_MEDIA_IP>/32`. Coturn derives its realm from the canonical TURN hostname; `WEBMEET_TURN_REALM` is not a provider output. Signaling hostname, media IP, TURN hostname, and TURN external IP are separate fields and must not be substituted for one another. The provider may output the scoped `WEB_PUBLISHING_CLOUDFLARED_TUNNEL_TOKEN` only as a sensitive Web Publishing-owned value already present in its resolved environment; it must never obtain that value by reading container secret-state. It must not output unused compatibility values such as `WEBMEET_TLS_HOSTNAME`, `WEBMEET_CERT_EMAIL`, or `WEBMEET_LIVEKIT_UPSTREAM`, nor generated or shared-generated service secrets such as `WEBMEET_LIVEKIT_API_KEY`, `WEBMEET_LIVEKIT_API_SECRET`, `WEBMEET_TURN_PASSWORD`, `WEBMEET_TURN_AUTH_SECRET`, `PLOINKY_WEBMEET_MASTER_KEY`, `ONLYOFFICE_JWT_SECRET`, or `JWT_SECRET`.

The legacy unscoped Cloudflare tunnel token name is not a Web Publishing input, output, alias, or documented setup path. Existing standalone `basic/cloudflared` users may continue to use the older connector agent, but Explorer QA/prod must not use it as a Web Publishing fallback.

Route validation must require HTTP or HTTPS origin URLs with explicit ports, reject raw Ploinky AgentServer/MCP port `7000`, enforce configured base-domain ownership for managed hostnames, and render deterministic nginx and Cloudflare ingress output. Exposure paths use a strict simple-URI grammar (slashes, unreserved characters, and valid percent-encoded octets only); whitespace, quotes, Nginx metacharacters, fragments, variables, and directive delimiters are rejected before rendering. The renderer defensively revalidates paths, services, canonical DNS hostnames, canonical IPv4 hostnames, and external proxy peers even when called without the route-model normalizer. The fixed manifest/Nginx listeners are not configurable fields; unsupported `lanHost` and `listenPort` inputs must not be advertised, persisted, or fingerprinted. The canonical LiveKit route cannot declare a custom path or share its hostname with another origin. nginx config reload is gated by `nginx -t`; generated configs and status payloads must not contain tokens, API keys, JWTs, cookies, generated secrets, or authorization headers.

LiveKit signaling is proxied only within the slash-delimited `/rtc` boundary: the exact `/rtc` path and descendants such as `/rtc/v1` and `/rtc/v1/validate` reach LiveKit. `/rtcevil`, every other unmatched path, `/twirp`, `/webhook`, and unmatched `Host` headers return 404 without proxying. Both the exact and descendant locations disable access logging and discard location-level upstream error logs because LiveKit join JWTs appear in query parameters; rate limits are 5 requests/second (burst 20) and 50 concurrent connections per effective client IP.

nginx separates local, Cloudflare, and external-TLS signaling trust boundaries. Local `tlsEdge=none` signaling uses port 8081. With a public TLS edge, the LiveKit hostname on raw 8081 returns 404. Cloudflare signaling uses the same-container `127.0.0.1:18081` connector; only that server block trusts `CF-Connecting-IP`, only from source `127.0.0.1`, rejects a missing header, and forwards `X-Forwarded-Proto=https`. External signaling uses container port 18083, published only as host `127.0.0.1:18083`. Nginx evaluates the original socket peer through `$realip_remote_addr` against the exact deployment-owned proxy list and returns 403 for every unlisted peer before it can trust `X-Real-IP`; this prevents an arbitrary sibling container on the shared bridge from spoofing client identity. A trusted peer with a missing `X-Real-IP` receives 400. Only then is the supplied address treated as the effective client address and `X-Forwarded-Proto=https` forwarded, so request and connection limit zones operate per external client rather than per reverse-proxy address. The trusted external proxy must terminate a valid certificate for `meet.<baseDomain>`, preserve that Host header, validate and overwrite `X-Real-IP` rather than passing through client input, and target the loopback-published connector. Port 18083 must never be publicly exposed. Neither connector targets raw LiveKit port 7880 from the public side. Private DNS-name upstreams, including the router, OnlyOffice, and LiveKit aliases, are placed in variables and resolved per request through validated IP resolvers read from the running container's `/etc/resolv.conf`, so `nginx -t` does not require sibling containers or aliases to exist yet.

Cloudflare DNS mutation is opt-in. API mode writes HTTP hostnames as proxied tunnel CNAMEs and writes `turn.<baseDomain>` as a separate DNS-only A record whose content is exactly `WEB_PUBLISHING_TURN_EXTERNAL_IP`; TURN never appears in HTTP tunnel ingress. Token mode starts the connector with a private ephemeral `--token-file` when the scoped token is configured, but its remotely managed tunnel configuration must independently target `http://127.0.0.1:18081` for the LiveKit hostname. The Web Publishing image pins Cloudflared at `2026.7.1`, a reviewed release newer than the `2025.4.0` token-file minimum; a mutable `latest` tag is not an acceptable compatibility contract. Selecting the `cloudflare` TLS-edge contract is an operator assertion that this trusted edge and connector route exist. When API mode creates a new tunnel, the returned token is written only to the private agent secret-state file and consumed there by the container supervisor; it is not promoted into Ploinky's host-side provider store. MCP responses and status payloads expose only presence flags.

LiveKit and TURN media remain explicit direct media-plane exposure in the WebMeet infra agent. Cloudflare HTTP tunnels can publish HTTP/WebSocket signaling, but they do not carry WebRTC UDP media. Web Publishing should warn operators when a selected mode could be mistaken for complete WebMeet media exposure.

## Decisions & Questions

### Question #1: Why is Web Publishing separate from the existing cloudflared agent?

Response:
The existing `cloudflared` agent is a standalone tunnel connector. Explorer QA/prod needs a richer owner for generated public topology, nginx route normalization, provider preflight, dashboard configuration, and Cloudflare API planning. Keeping that in a new agent avoids changing the standalone connector contract and makes Explorer's cutover explicit.

### Question #2: Why does the dashboard use Explorer settings plus admin MCP instead of a public route?

Response:
Publishing configuration can affect internet-facing routes and Cloudflare DNS. It belongs behind Explorer admin settings and router-mediated admin MCP tools. A public dashboard HTTP route would widen the attack surface without adding needed capability.

### Question #3: Why are WebMeet and OnlyOffice generated secrets excluded from provider output?

Response:
Those secrets are already owned by Ploinky generated/shared-generated secret mechanics in their respective agents. Web Publishing owns public topology and provider-owned external credentials, not service credentials derived from the workspace master key.

### Question #4: Why keep LiveKit/TURN media outside the Cloudflare tunnel contract?

Response:
Cloudflare Tunnel handles HTTP/WebSocket traffic. LiveKit and TURN media require explicit TCP/UDP media-plane exposure and cannot be hidden behind the Ploinky router or a Cloudflare HTTP tunnel without changing the WebRTC architecture.

### Question #5: Why are public IPs explicit instead of auto-detected?

Response:
The LiveKit media address and Coturn relay address can differ, especially behind separate L4 endpoints or NAT. Auto-detection can advertise an internal bridge address or silently couple the two planes. Separate validated IPv4 inputs make the topology reviewable, let the provider generate Coturn's single `/32` peer ACL from the canonical LiveKit media IP, and keep public startup fail-closed.

### Question #6: Why does deployment env override saved dashboard topology?

Response:
Deployment env is the active infrastructure contract for the running workspace, while saved dashboard state is an operator convenience that can outlive a deployment or domain. Using one shared merge path for provider output, supervision, and saved-state reads prevents them from serving and advertising different topologies. Persisted normalized `service` values are derived from `originId`, so recomputing them lets a same-domain upgrade adopt a hardened canonical upstream without discarding the operator's hostname/path selection or failing only after shutdown. When the env-owned base domain changes, discarding concrete old-domain exposures is safer than retaining routes that point browsers at stale signaling, media, or TURN endpoints. Explicit validation/apply request payloads remain authoritative for the operation being requested.

### Question #7: Why is `/data` sticky-world-writable with Podman chown disabled?

Response:
The image's non-root UID cannot write a fresh host-owned `0755` bind directory under Linux Docker, while Podman's `:U` ownership transfer can make container-owned `0600` files unreadable to the host-side startup provider. A sticky `01777` directory is the portable shared-directory contract: the container can atomically write its own files under either runtime, unrelated local users cannot replace those files, and host ownership stays stable. Only non-secret `0644` config/status state crosses the host/container read boundary. The `0600` secret-state file remains container-only, and the provider is designed not to read it.

### Question #8: Why does an external TLS edge use a separate connector instead of port 8081?

Response:
An ordinary HTTP reverse proxy connects to nginx from one proxy address. Rate-limiting raw 8081 by that address would collapse every browser into one shared 5r/s and 50-connection bucket, while trusting forwarded headers on the ordinary listener would let direct clients spoof their identity. Port 18083 creates a narrow proxy-only trust boundary: the host publishes it only on loopback, Nginx admits only exact deployment-configured proxy peers, a trusted TLS proxy must overwrite `X-Real-IP`, missing identity fails closed, and raw 8081 continues to ignore forwarded client identity and refuses public LiveKit signaling. Exact host CIDRs are required because a bridge-wide CIDR would recreate the sibling-container spoofing risk. OnlyOffice no longer owns a direct host port; its local browser route is consolidated through the ordinary loopback Nginx listener on 8081.

### Question #9: Why is the AgentServer mapping first, and how does Nginx still gate startup?

Response:
Ploinky's generic route selects the explicit mapping for container port `7000` when one exists; otherwise it falls back to the first declared port. Web Publishing must declare public Nginx sockets, so it cannot receive Ploinky's implicit AgentServer mapping. A stable first mapping of `127.0.0.1:17003:7000` restores the normal MCP target while keeping it on loopback and leaving `8081` as the intentional Nginx boundary socket. The AgentServer command waits for an actual TCP connection to Nginx before launching, then MCP readiness proves the gated sidecar is operational. This preserves startup ordering without adding Web Publishing knowledge to Ploinky.

### Question #10: Why do Nginx and Cloudflared exits stop the supervisor?

Response:
The container's long-lived process is the health boundary for the publishing data plane. Keeping that process alive after required Nginx or Cloudflared has exited would let orchestration and the MCP sidecar report a healthy agent while browser signaling is unavailable. Treating required-child loss as fatal gives the container runtime an observable nonzero failure and a chance to apply its normal restart policy. Plain Nginx disables Cloudflared. Unprovisioned API mode is the only non-running control-ready state: it supervises Nginx so an administrator can create the first tunnel, but reports `awaiting-provision` until the resulting token is installed by a restart. Token mode and provisioned API mode require a live Cloudflared child.

### Question #11: Why does configuration apply require a restart instead of signaling child processes?

Response:
Nginx can reload one file in place, but a publishing-mode change may also add, remove, or re-key the required Cloudflared connector and change provider outputs consumed by sibling services. Treating those independent transitions as one reliable hot reload would require a new transactional process-control protocol. The explicit fingerprint and restart-required response use the existing container lifecycle as that transaction boundary. Its non-secret connector identity prevents an old running tunnel from authorizing remote mutation for a newly requested tunnel. Cloudflare ingress is held back until the restarted supervisor proves that its local topology, connector identity, and required children match, so no remote `Applied` result can mask a stale local data plane.

## Conclusion

`agent:basic/web-publishing` is the Explorer-facing public topology owner for QA and production. It keeps the control plane admin-only, persists provider output through Ploinky's startup provider contract, treats DNS mutation as opt-in, and preserves generated-secret, media-plane, and network trust-zone boundaries.
